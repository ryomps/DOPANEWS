# 複数ソースによるニュース作成の設計

状態：初期版を実装済み。Yahoo!公式RSSの主要・経済・科学の見出し取得、公的なHTML原資料の検索・取得、根拠付き事実一覧、独自原稿、原稿審判、ローカル保存、ラップ生成への接続に対応。
確認日：2026年10月29日。既存の公的資料に基づく固定記事は変更しない。

### UIと歌詞生成の更新

- 審判の状態・判定・指摘・専用ボタンは全画面で非表示。記事の審判に通らない原稿も表示せず、作成失敗として扱う。
- 歌詞は初回を含めて最大3回まで自動修正し、合格後だけMurekaで1曲生成する。上限到達、または確認処理の通信障害時は停止する。原稿・音源の自動再生成は追加しない。

### 初期版の実装範囲

- 報道本文の自動比較は未対応。指定8サイトのうちYahoo!の見出しのみ自動取得し、他7サイトは参照リンクと対応状況を表示する。
- 原資料は `www.caa.go.jp`・`www.stat.go.jp`・`www.mext.go.jp` のHTML本文に限定し、リダイレクト・PDF・第三者の利用条件が明示されたページは採用しない。一次資料の個別の権利除外は抽出時・校閲時にも確認するが、機械判定だけで権利処理を保証はしない。
- 見出しは15分キャッシュ。検索はOpenAI Responses APIのgpt-6-luna、事実抽出・執筆・原稿審判はGemini 3.1 Flash-Lite。OpenAIは1話題1回、1日5回、試験累計20回、ツール1回・最大出力800トークンに制限。検索結果を保存して再利用する。失敗時の自動再試行はしない。
- 取得本文内の根拠引用、段落の事実ID、最低2件の異なる本文資料をコードで検証する。複数サイトによる全事実の独立確認を保証したとは扱わない。
- 保存先は `.local/news/`。保存済みの記事にはAPIを再使用しない。保留記事の再調査には前回の校閲指摘を渡し、ユーザーが選択した場合だけ再実行する。
- ラップの作詞・審判には採用事実と根拠原文を渡す。ニュースの生成原稿をその原稿自身の根拠にしない。

## 目的と操作

ユーザーはURLや記事本文を入力せず、アプリ内の話題一覧から選ぶ。
アプリが関連報道と一次資料を調べ、根拠を保存した事実一覧、独自の解説記事、歌詞の順に作成する。
記事を開くだけでは生成APIを呼ばない。「この話題を調べる」で調査・執筆を開始し、使用するAPIを表示する。
審判に合格した後は既存のMureka 9（1曲）生成へ接続する。原稿の問題・判断保留・取得失敗では自動再生成しない。歌詞の内容不合格は最大3回の枠内で自動修正する。

## ユーザーが指定した候補

「候補」は自動取得や生成利用の許諾を取得済みという意味ではない。
RSSの提供と、取得した情報の再配信・AI処理・改変への許諾は別々に確認する。
外部検索・外部プロキシを使うことを、原サイトの利用条件やアクセス制限を回避する手段にしない。

## 処理の境界

1. 配信元ごとに、見出し一覧取得・本文取得・AIへの入力・保存・公開の可否と根拠を管理する。
2. 利用可能なRSS・APIで見出し・日時・リンクを取得する。障害を空一覧や古い速報と偽らず、取得時刻と更新失敗を表示する。
3. 選択された話題について関連報道を集める。見出しが似ているだけの別事件・別年度を混ぜない。
4. 官公庁、統計、研究機関、企業の原発表等を探し、各サイトの利用条件を確認して取得する。
5. 根拠資料の取得済み本文と事実を対応させる。URLが存在するだけ、検索結果に出ただけでは内容確認済みとしない。
6. 記事は採用した事実から執筆し、文ごとに事実IDを付ける。取得した記事の指示文をAIへの指示として扱わない。
7. 原稿審判は元資料・事実一覧と照合する。生成原稿だけを根拠に自己確認しない。
8. 歌詞審判にも採用事実・元資料を渡す。合格した場合のみ既存の音源生成を開始する。

## 保存する情報

- `sources`：資料ID、配信元、実際の報道元、正規URL、公表日時、取得日時、取得状態、利用条件の記録、本文ハッシュ。
- `facts`：事実ID、日時・主体・出来事・数値・単位・対象期間・未確定事項、根拠となる資料IDと本文内の該当箇所。
- `conflicts`：資料間で異なる数値・期間・主張、訂正情報、解消済みかどうか。
- `article`：見出し、独自の解説文、段落ごとの事実ID、作成日時、使ったモデル、原稿審判結果。
- `research`：実際に参照した資料、未取得・有料・利用条件未確認の資料、同一配信記事の重複、調査時点。

事実一覧・原稿・審判結果は `.local/` に保存し、ラップの保存記録から参照可能にする。
保存済み原稿を開くたびに調査をやり直さない。新しい調査は明示的な更新操作とする。
本文を保存できない配信元については、その保存許可がある前提のキャッシュを作らない。

## 確認状態の扱い

- 掲載サイト数と独立した報道元数を別に数える。同じ通信社記事の転載は、独立した複数確認として数えない。
- 一次資料が見つかっても、それが裏付ける範囲だけを確認済みとする。一次資料だから全主張が正しいとは表示しない。
- 二つの資料が食い違うときは多数決で採用せず、原発表・訂正・対象期間を確認する。
- 独自取材・インタビューの情報は別枠にする。発言の確認と、発言内容が事実かの確認を区別する。
- 未取得、有料、利用条件未確認の本文は根拠に含めない。情報不足なら生成を停止して理由を表示する。
- 「公開日時」「出来事の日」「取得日時」を分け、古い記事を現在の出来事として提示しない。

## 実装順序

1. 配信元レジストリと、利用できる見出しフィードからの候補選択UI。
2. 話題単位の関連資料収集、原資料の取得状態と根拠付き事実一覧。
3. 事実IDに基づく独自原稿と原稿審判、ローカル保存・再利用。
4. 既存の歌詞審判・Mureka 9への接続、保存音源から根拠資料への表示。

最初の候補取得は公式RSSを確認できたYahoo!ニュースから検討する。ただし見出しだけで本文の事実確認や歌詞化はしない。
他の指定サイトは接続方法・利用条件が確認できた機能から個別に有効化する。
実装の受入確認では、重複配信、記事訂正、取得失敗、根拠不足、日時・単位の混同、原稿の根拠外の断定、自動課金の有無を検証する。
